TCP, UDP and the ports they deliver to

About 10 minutes. By the end you can explain why "the server is up" and "the app works" are two different questions, and test the second one yourself.

Why this matters at work

A user can reach a server (it answers a ping) but the app on it won't connect. The four settings from lesson 0001 got traffic to the right machine. Getting it to the right program on that machine is a separate step, handled by port numbers. A firewall that blocks one port breaks one app while everything else looks fine.

IP is the truck, TCP and UDP are the boxes

An IP packet carries data from one address to another, like a truck that knows the street address but not which room the parcel is for.[1] Inside the packet rides a second layer: either TCP or UDP. Both add port numbers, which say which program should receive the data.

TCPUDP
StyleConnection-oriented: sets up a conversation firstConnectionless: just sends
Reliable?Yes. Lost data is re-sent, and data arrives in orderNo. Lost data stays lost
Flow controlYes. The receiver can say "slow down"No
Good forWeb pages, email, file transfers, remote desktopLive voice and video, DNS lookups, DHCP

Coming from programming: TCP is like a function call that waits for a return value and retries on failure. UDP is fire-and-forget. For a phone call, a late packet is useless anyway, so UDP's speed wins over TCP's guarantees.[1]

Remember DHCP from lesson 0001? It uses UDP. A device without an IP address can't set up a TCP conversation yet, so it shouts a UDP broadcast instead.

Port numbers

A port is a number from 0 to 65,535, and TCP and UDP each have their own full set.[1] One server with one IP address can run a web server, a mail server and a file share at once, because each listens on its own port.

  • Non-ephemeral ports are permanent. Servers listen on them. The well-known ones are usually 0–1023, such as 443 for HTTPS.[1]
  • Ephemeral ports are temporary. The client picks one at random for each connection so replies find their way back, then drops it when done.

So every connection has two ends, each an address plus a port:

Client  192.0.2.10 : 51544   (ephemeral, picked by the laptop)
   ⇅  TCP
Server  198.51.100.7 : 443   (non-ephemeral, HTTPS)
Rule of thumb

Ping works but the app doesn't? The machine is reachable, so suspect the port: the service isn't running, or a firewall blocks that port.

Try it (2 minutes)

PowerShell's Test-NetConnection tries to open a TCP connection to a port and tells you if it worked.[2]

  1. Open PowerShell and run Test-NetConnection example.com -Port 443.
  2. Look for TcpTestSucceeded : True. Something on that server answered on port 443.
  3. Now try a port nothing listens on: Test-NetConnection example.com -Port 8123. It waits, then shows False.
ComputerName     : example.com
RemoteAddress    : 203.0.113.80
RemotePort       : 443
InterfaceAlias   : Ethernet
SourceAddress    : 192.0.2.10
TcpTestSucceeded : True

Addresses above are documentation examples. Your output will differ. It only tests TCP: there's no "connection" to test with UDP.

Practice

Answer from memory before scrolling back up.

A user's PC can ping a file server, but the file-sharing app times out. Other users connect fine. What's the best next suspect?

A working ping proves the address, gateway and routing are fine, so DNS, IP changes and APIPA are ruled out. Reaching the machine but not the program points at the port: most often a firewall on this PC or path blocking it.

A video call stutters on a busy network, but it never pauses to re-send lost audio. Which protocol is it most likely using?

Live voice and video usually ride UDP. It doesn't re-send lost data, so you get a glitch instead of a delay. TCP would stop and re-send, which is worse for a live conversation. And IP alone has no ports, so it couldn't reach the app.

Your laptop opens two browser tabs to the same HTTPS server. How does it keep the two replies apart?

Both tabs talk to the same server port (443). The laptop picks a different temporary, ephemeral port for each connection, so each reply comes back to the right tab.

Test-NetConnection to a server on port 3389 returns TcpTestSucceeded : False. What does that tell you for sure?

False only means the TCP connection to that port didn't open. The server may be on with the service stopped, or a firewall may block the port. Account rights come later, after a connection exists. A missing DNS record would fail earlier, before any port test.

From memory: give two differences between TCP and UDP, and the job of an ephemeral port. (then click to check)

TCP is connection-oriented, reliable (re-sends, keeps order) and has flow control. UDP is connectionless, with no re-sending and no flow control, so it's lighter and faster. An ephemeral port is the temporary port a client picks for one connection, so the reply finds its way back.

Review: earlier lessons

Spaced retrieval: pull these from memory first, then check.

A laptop's ipconfig /all shows 169.254.20.5 and a blank default gateway. What happened, and where do you look? (lesson 0001)

That's APIPA: no DHCP server answered, so Windows made up a link-local address. Look at the connection to DHCP (cable, Wi-Fi, switch port, or the DHCP server), not the user's account.

A PC reaches websites by IP address but not by name. Which of the four settings is wrong? (lesson 0001)

DNS. Reaching an IP address proves the IP address, mask and gateway work. Only turning names into addresses fails.

Name the four settings a device needs, and which one decides whether an address is local. (lesson 0001)

IP address, subnet mask, default gateway, DNS server. The subnet mask decides what's local; everything else goes to the gateway.
