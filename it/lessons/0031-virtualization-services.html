Where the hypervisor lives: type 1, type 2, VDI and containers

About 10 minutes. Yesterday was why we run virtual machines. Today is how they're delivered: where the hypervisor sits, what the CPU and network must provide, and two neighbours of the VM, virtual desktops and containers.[1] The win: given a scenario, pick the right one of these and say why.

Why this matters at work

Cloud PCs and hosted virtual desktops are VDI. They're enrolled and managed in Intune like a physical laptop, with the same Entra sign-in and the same compliance and configuration policies.[5] When a user says "my computer is slow" and their computer is a virtual desktop, the problem may be in the data center or their home connection, not in the device on their desk.

Type 1 vs. type 2 hypervisor

Type 1 (bare metal, native)Type 2 (hosted)
Runs onDirectly on the hardware[1]On top of a normal OS (Windows, macOS, Linux)[2]
Typical homeServers and data centersA technician's or developer's desktop
OverheadLess: no host OS in the wayMore: the host OS takes its share first
ExamplesVMware ESXi, Microsoft Hyper-V, ProxmoxOracle VirtualBox, VMware Workstation

Gotcha: turning on Hyper-V in Windows 11 doesn't make it type 2. The hypervisor loads first, and Windows itself then runs on top of it in the root partition, the one partition allowed to touch the hardware.[3] That's why systeminfo says "A hypervisor has been detected" once Hyper-V is on.

What the hardware must give

  • CPU support: the processor needs virtualization extensions, Intel VT-x or AMD-V, switched on in the UEFI/BIOS.[1] Lesson 0030's Task Manager check (Virtualization: Enabled) is this. Hyper-V also wants SLAT (second-level address translation), a CPU feature that speeds up VM memory.[8]
  • Enough memory and disk: every running VM takes its RAM out of the host's.
  • A network plan: the hypervisor gives each VM a virtual NIC plugged into a virtual switch. Three modes to know:
ModeWhat the VM getsHyper-V switch name
Shared address (NAT)Goes out using the host's IP address. Can reach the network; others can't start a connection to it.(the built-in Default Switch)
BridgedIts own MAC and its own IP from the real network's DHCP server. Looks like any other device on the LAN.External
Private / host-onlyTalks only to other VMs (and sometimes the host). No route out: good for isolated tests.Private (VMs only) or Internal (VMs + host)

Sources: VM network modes [4]; Hyper-V external, internal and private switches [6].

VDI: the desktop lives elsewhere

Virtual desktop infrastructure (VDI) runs each user's desktop as a VM in a data center or the cloud. The user's device only shows the screen and sends keyboard and mouse input, so it can be a thin client, an old laptop, or a tablet.[1] Data stays in the data center, the desktop follows the user to any device, and a lost laptop holds nothing. The cost: no network, no desktop, and lag shows up as a "slow computer".

Containers: share the kernel, ship the app

A VM carries a whole operating system, kernel included. A container carries only the app and what it needs, and shares the host OS kernel.[7] So containers are small and start in seconds, and the same container image runs the same way on a laptop, a server or the cloud (Docker is the well-known tool). The trade-off: containers are more lightly isolated than VMs, and a container built for Linux needs a Linux kernel underneath.[7]

Memory hook

Type 1 sits on the metal; type 2 sits on an OS. NAT shares the host's address; bridged gets its own; private goes nowhere. VDI moves the desktop; containers share the kernel.

Try it (3 minutes)

  1. Run systeminfo and read the last lines again. "A hypervisor has been detected" means a type 1 hypervisor is already running underneath your Windows (Hyper-V, or a feature built on it such as Windows Sandbox or WSL 2).
  2. If Hyper-V is on (Pro, Enterprise or Education), open an admin PowerShell and list the virtual switches: 
    Get-VMSwitch | Select-Object Name, SwitchType
    You'll likely see Default Switch as Internal with NAT behind it. Hyper-V Manager → Virtual Switch Manager shows the three types you can create: External, Internal, Private.
  3. Inside any VM, Task Manager → Performance → CPU shows Virtual machine: Yes. Handy when you're not sure whether the desktop you've remoted into is real or virtual.

On a work laptop, look but don't change switches: a new external switch takes over the physical network adapter.

Practice

Answer from memory before scrolling back up.

A small company wants to replace five aging servers with one powerful server running five VMs, with as little overhead as possible. What should run on the new server?

A type 1 (bare-metal) hypervisor runs directly on the hardware, so no host OS takes its share of the resources first. That's the data-center choice. Type 2 runs on top of a desktop OS (more overhead), Windows Sandbox is a disposable single VM, and five physical servers is what they're replacing.

A technician builds a test VM that must get its own IP address from the office DHCP server and appear on the network like any other computer. Which network mode?

Bridged (a Hyper-V external switch) connects the VM straight to the real network: its own MAC, its own DHCP lease. NAT hides it behind the host's address; private and internal keep it off the real network entirely.

Contractors need a company Windows desktop with internal apps, from their own laptops, and company data must never be stored on those laptops. What fits best?

With VDI the desktop and its data stay in the data center or cloud; the contractor's laptop only shows the screen. Installing, syncing or running a container locally all put company software or data on a device the company doesn't own.

A developer's app starts in about a second as a container, but takes minutes when packaged as a full VM. What explains the difference?

A container doesn't boot an operating system: it shares the host's kernel and carries only the app and its dependencies. A VM has to start its own complete OS first. Containers still have networking, and they don't boot a BIOS at all.

From memory: type 1 vs. type 2, the two CPU extensions, the three network modes, and how a container differs from a VM. (then click to check)

Type 1: on the hardware (ESXi, Hyper-V). Type 2: on a host OS (VirtualBox, Workstation). CPU: Intel VT-x / AMD-V, enabled in UEFI/BIOS. Network: NAT (share the host's IP), bridged (own IP on the real LAN), private (VMs only). A container shares the host's kernel and carries only the app; a VM carries a whole OS.

Review: earlier lessons

Spaced retrieval: pull these from memory first, then check.

An employee leaves. Their personal phone was enrolled as BYOD with work email. Retire or wipe, and what does each remove? (lesson 0028, 3 days ago)

Retire (selective wipe): removes company apps, data, email profiles and settings, and leaves personal data alone. That's the right one for BYOD. Wipe is a factory reset of the whole phone, for company-owned devices.

A laptop's camera shows a black image in a video call. Name the four layers to check, in order. (lesson 0024, 7 days ago)

Physical (privacy shutter, function key) → Windows privacy settings (including the desktop-apps switch) → device (Device Manager / Get-PnpDevice, status OK) → policy (greyed-out settings mean it's managed). A black image with everything else fine is usually a closed shutter.

You bridge a new VM onto a test network that has no DHCP server. It shows an address starting with 169.254 and no gateway. What happened? (lesson 0001, 30 days ago)

No DHCP server answered, so Windows gave itself an APIPA (link-local) address in 169.254.0.0/16. It has no gateway and no DNS server, so it can reach almost nothing. Add a DHCP server to that network or set a static address.
