Copy, don't change: how the filter panel holds its state

About 10 minutes. By the end you can read the update helper in Board Games for Two, say why it builds a new object instead of editing the old one, and predict what the screen does if it didn't.

What got built this week

Nothing new in two-player-bg-finder: the last commit is still 3a77ac7 (2026-09-26). So this week we read code that already exists. Last week was what the filter does (applyFilters). This week is where the filter settings live and how a click changes them: the top of web/src/GamesBrowser.tsx, from the filter panel commit 26bb9e1.

1. One object holds every filter

The whole filter panel (name box, checkboxes, chips, ranges) is driven by one line:

const [filters, setFilters] = useState(emptyFilters);
  • useState gives a component memory that survives between renders. It returns a pair: the current value and a function to replace it.[1]
  • const [a, b] = ... is array destructuring: unpack the pair into two names. It's C#'s tuple deconstruction, var (filters, setFilters) = ....[2]
  • Notice emptyFilters has no parentheses. Passing the function itself makes it an initializer: React calls it once, on the first render, and keeps the result.[1] The result is a plain object, typed in filters.ts:
export type Filters = {
  name: string;
  types: string[];
  ranges: Partial<Record<RangeKey, Range>>;
  tags: Partial<Record<TagKey, string[]>>;
  mustPlay: number[];
  twoOnly: TwoOnly;
};

Why one object? Because applyFilters(games, filters) needs all of it at once, and the "Clear all" button can reset everything in one call: setFilters(emptyFilters()) (with parentheses this time: a fresh object, built now).

2. React only notices a new object

Coming from C#, you might expect the UI to watch the object's fields, like WPF with INotifyPropertyChanged. React doesn't. It learns about a change only when you call setFilters, and then it compares old and new with Object.is, which for objects is like C#'s ReferenceEquals. Same object? React skips the re-render.[1]

So the rule from the React docs is: treat state as read-only, and replace it rather than mutate it.[3] That's exactly what the AI wrote in the helper every input uses:

const update = (patch: Partial<Filters>) =>
  setFilters((f) => ({ ...f, ...patch }));

Read it in three steps:

  1. patch: Partial<Filters>: just the fields that changed, e.g. { types: ["Family"] } (Partial is from lesson 0002).
  2. (f) => ... passed to setFilters is an updater function: React hands it the latest state f and stores whatever it returns.[1] The extra parentheses in ({ ... }) tell JavaScript "this brace is an object, not a function body".
  3. { ...f, ...patch }: a new object with every field of f, then the patch on top (later wins, as in 0002). In C# terms: f with { Types = ... } on a record. New reference, so React re-renders.

Nested data gets the same treatment one level down. setTag copies tags too, and [key]: values is a computed key: the property's name comes from the variable key (like dict[key] = values, but inside a new object):[2]

setFilters((f) => ({ ...f, tags: { ...f.tags, [key]: values } }));

Arrays follow the rule as well. The "Must play" checkbox adds a number with spread instead of push, and removes one with filter (which, from lesson 0002, returns a new array):[4]

e.target.checked ? [...filters.mustPlay, n] : filters.mustPlay.filter((x) => x !== n)
The big idea

State in React is a snapshot, like an immutable C# record. To change it, build a new one and hand it to the setter. React compares references, not contents: change the old object in place and React sees "same object", does nothing, and the screen goes stale.

3. Controlled checkboxes: the box shows the state

Here is one popular-type chip (from the small Chips component):

<input
  type="checkbox"
  checked={value.includes(o)}
  onChange={(e) => onChange(e.target.checked ? [...value, o] : value.filter((x) => x !== o))}
/>

In JSX, { } means "evaluate this JavaScript here". Giving a checkbox a checked value makes it controlled: the tick is drawn from state, and onChange is how a click asks for new state.[5] The browser's own tick no longer decides anything.

Why this matters here: the panel shows "Family" twice, as a chip and in the "More types" dropdown. Both get value={filters.types}. One state, two views, so they can't disagree. The panel test even says so in a comment: "Popular chips and the full lists share state."

Practice

What does const [filters, setFilters] = useState(emptyFilters); do on the first render?

A function passed to useState is an initializer: React calls it once and stores the return value, the empty Filters object. It isn't called again on later renders (that's the point of leaving off the parentheses), and the state belongs to this one GamesBrowser, not to every component.

Someone "simplifies" the helper to setFilters((f) => Object.assign(f, patch)). Object.assign copies the patch's fields into f and returns that same f. What happens when you tick "Family"?

The field really changes, but f is the same object, so Object.is(old, new) is true and React skips the re-render. It compiles fine. I tried it: the panel test fails right at the Family click with expected [ '1', '2' ] to deeply equal [ '2' ], meaning the table still shows both games.

What breaks if we delete checked={value.includes(o)} from the chip checkbox in Chips?

Without checked the box is uncontrolled: the browser keeps its own tick. Tick "Family" in the More types dropdown and the filter works, but the Family chip stays unticked; press Clear all and the chips stay ticked while the filter is off. checked is optional, so TypeScript is happy. And surprise: I tried it, and all 23 tests still pass. No test checks that the chip's tick follows the state. Passing tests are evidence, not proof.

Which expression adds n to the must-play list the way React wants?

Spread builds a new array with the old items plus n. push, unshift and splice all change the existing array in place, which the React docs list as methods to avoid on state.

The name box, the Types chips, Must play and the 2p-only radios go "dead": the table and the count don't move. Mechanics chips and ranges still work, because setTag and setRange still build new objects. One test fails, the big panel test, at its first update-driven step (the Family chip). The Mechanics clicks just before it pass, matching your prediction if you traced who calls what. Bonus: after a dead click, tick a Mechanics chip. The table suddenly catches up on both changes, because the earlier mutation was really there; React just hadn't been told.

Spaced review from lesson 0002: emptyFilters() starts with mustPlay: []. Why does that not hide every game? (answer, then click)

The must-play condition is f.mustPlay.every((n) => plays(g, n)), and every on an empty array is true ("all of nothing"), like LINQ's All. So every game passes. If it were some, an empty array would give false and the list would be empty.
