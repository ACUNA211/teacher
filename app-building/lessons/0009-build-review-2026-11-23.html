What got built this week

Nothing new in two-player-bg-finder. The last commit is still 3a77ac7 (2026-09-26), so we read existing code again. Every file you've opened in this course starts with a few import lines that we've skipped past. Today they're the lesson.

1. It starts in index.html

In a C# console app, the runtime looks for Main. A web app has no Main: the browser loads an HTML page, and the page says which code to run. Here's the whole body of web/index.html:

<body>
  <div id="root"></div>
  <script type="module" src="/src/main.tsx"></script>
</body>

An empty div and one script. Vite's docs call index.html "the entry point to your application": Vite reads it as source code and follows that <script type="module" src> into your TypeScript.[2] The type="module" part matters. It tells the browser this file is an ES module, so it may use import and export, and it runs in its own scope.[1]

That script is src/main.tsx, the real Main:

import { StrictMode } from "react";
import { createRoot } from "react-dom/client";
import { App } from "./App";
import "./index.css";

createRoot(document.getElementById("root")!).render(
  <StrictMode>
    <App />
  </StrictMode>,
);

It finds the empty div and tells React to draw <App /> inside it. The ! is TypeScript's non-null assertion: getElementById returns "an element or null", and ! says "trust me, it isn't null". Like lesson 0006's as HTMLInputElement, it's a promise, not a check: no code is added, and if the div were missing it would crash at run time.[3]

From here, each file pulls in the next. Following the import lines gives this module graph:

index.html
└─ main.tsx ──── react, react-dom/client, index.css
   └─ App.tsx ── react
      ├─ Footer.tsx
      ├─ GamesBrowser.tsx ── filters.ts
      │  └─ GamesTable.tsx ── @tanstack/react-table
      └─ types.ts   (types only: gone before the browser runs)

This graph is also how vite build decides what goes into the bundle: anything no import reaches, like the test files, stays out (that's why moving Vitest in lesson 0008 changed nothing for visitors).

2. export is public; everything else is private

In C#, a class is visible across the project unless you say otherwise. A JavaScript module is the opposite: everything declared in a file is private to that file unless it's exported.[1] So a file is roughly a C# static class where export means public. From filters.ts:

export const VOTE_FLOOR = 15;
export function applyFilters(games: Game[], f: Filters): Game[] { … }

and in GamesBrowser.tsx, the other side:

import { activeCount, applyFilters, emptyFilters, VOTE_FLOOR, type Filters, … } from "./filters";
const MORE_TAGS = TAG_FIELDS.filter(…);   // no export: only this file can see it

Three things to read in an import line:

  • Curly braces = named imports. The names must match the export names exactly. Like using static in C#, but you list each member you want. Imported names are read-only: you can't reassign VOTE_FLOOR from another file.[1]
  • No braces = the default import. A module may also have one export default, imported without braces under any name you like.[1] This repo uses named exports for its own code; the one default is in vite.config.ts (export default defineConfig(…)), because Vite reads the config file's default export.
  • type = gone at run time. import type { Game } from "./types" (and the inline type Filters above) can only bring in types. Use one as a value and tsc stops with an error.[4] Vite's docs recommend this syntax so type-only imports never get bundled by mistake.[5] It's lesson 0001 again: types.ts describes data, so nothing from it needs to exist in the browser.

3. The string after from: "./App" vs "react"

  • Starts with ./ or ../: a file path, relative to this file. "./App" is src/App.tsx (the bundler lets you leave off .tsx).
  • A bare name like "react" or "@tanstack/react-table": a package from node_modules, the ones listed in package.json (lesson 0008). Browsers can't resolve bare names on their own: Vite's docs say such an import "will throw an error in the browser", so Vite rewrites it to a real URL under /node_modules/.vite/deps/.[5] In C# terms, "./App" is a project reference and "react" is a NuGet package.
  • No names at all: import "./index.css" imports a file just for its side effect. For CSS, Vite injects the file's contents into the page in a <style> tag.[5] Without Vite, a browser can't import CSS with this plain line; it's a Vite feature.
The big idea

The browser runs one file, main.tsx, named in index.html. Everything else arrives because some file imported it. A file shares only what it exports; { braces } pick named exports, no braces picks the default, type imports vanish before run time, and a path without ./ means a package. When an AI's change breaks with "is not exported" or "has no default export", the fix is in these first lines, not the logic below them.

Practice

An AI deletes the word export from export function Footer(…) in Footer.tsx. What happens?

Without export, Footer is private to its file. Both App.tsx and Footer.test.tsx import it by name, so tsc (and npm run build) fails with an error that Footer is declared locally but not exported, and the test file can't load either. React never looks things up by name; it only uses what you import.

An AI "tidies" main.tsx to import App from "./App"; (no braces). App.tsx is unchanged. What happens?

No braces means "the default export", and App.tsx only has a named export (export function App). tsc reports that the module has no default export. Fix it either way round: put the braces back, or change App.tsx to export default function App. Braces aren't style; they choose which export you get.

What does the line import type { Game } from "./types"; leave in the JavaScript the browser runs?

Type-only imports are erased with the rest of the types, so the browser never sees the line. That's also why nothing checks games.json against Game at run time (lesson 0001): the type only exists while tsc is checking your code.

Why does from "react" have no ./ while from "./App" does?

A bare name means "a package": it comes from node_modules, installed from package.json. A name starting with ./ is a path to one of your own files. They aren't interchangeable: from "App" would look for a package called App and fail. Browsers don't ship React, and can't resolve bare names at all, which is why Vite rewrites them.

Spaced review from lesson 0005: App.tsx has {data && <Footer … />}. Why is && safe here, when it wasn't safe with a count? (answer, then click)

data is either an object or null. If it's null, && gives null and React draws nothing. The trap is a number on the left: 0 && … gives 0, and React draws a literal "0" on the page. An object or null can never be 0.
