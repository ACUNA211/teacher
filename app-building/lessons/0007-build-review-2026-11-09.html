Lists need keys: .map() and key

About 10 minutes. By the end you can read any "draw one of these per item" block in Board Games for Two, say what the key prop is for, and spot when a key is weaker than it looks.

What got built this week

Nothing new in two-player-bg-finder. The last commit is still 3a77ac7 (2026-09-26), so we read existing code again. Every chip, dropdown option, table row and cell in the app comes from the same pattern, an array mapped to JSX. Earlier lessons used .map() without stopping on it. Today we stop.

1. One array in, one list of elements out

Here are the three "2p-only games" radio buttons (Any, Only, Hide), from GamesBrowser.tsx line 27 and lines 89–94:

const TWO_ONLY: [TwoOnly, string][] = [["any", "Any"], ["only", "Only"], ["hide", "Hide"]];
…
{TWO_ONLY.map(([value, label]) => (
  <label key={value} className="chip">
    <input type="radio" name="two-only" checked={filters.twoOnly === value} onChange={() => update({ twoOnly: value })} />
    {label}
  </label>
))}

Read it from the outside in:

  • [TwoOnly, string][] is an array of tuples. [TwoOnly, string] means "exactly two items: first a TwoOnly (the union "any" | "only" | "hide" from filters.ts), then a string". Then the trailing [] makes it an array of those pairs. In C# it would be (TwoOnly Value, string Label)[].[2]
  • .map(fn) calls fn once per item and returns a new array of the results. It's LINQ's Select, or Python's [fn(x) for x in xs].[3] Here each result is a <label>, so you get an array of three elements, and React draws an array of elements one after another.[1]
  • ([value, label]) => is array destructuring in the parameter list: the function receives one pair and unpacks it into two names. C#: var (value, label) = pair;. Python: value, label = pair. Lesson 0004 showed the same trick with braces for objects ({ label, children }). Square brackets unpack by position, braces unpack by name.[3]
  • => ( … ): parentheses, not braces, so the arrow function returns the JSX directly, with no return keyword.

Because of the tuple type, TypeScript knows value is a TwoOnly, so update({ twoOnly: value }) type-checks. Write a typo like ["hdie", "Hide"] in the array and the build fails.

2. Why key?

On every render React gets a fresh array of elements and has to work out what changed since last time. Was an item added, removed or moved, or just updated? key is the name tag that lets it match old items to new ones. React's docs: keys "tell React which array item each component corresponds to, so that it can match them up later".[1]

The rules are short:[1]

  • Unique among siblings (the same key can appear in a different list).
  • Stable: the same item gets the same key on every render. Never key={Math.random()}.
  • From the data, ideally an ID. Here value ("any", "only", "hide") is perfect: unique and never changes.

Leave key off and the app still works. In development React prints Each child in a list should have a unique "key" prop. to the console (that's the exact text in React 19.3's source) and quietly uses each item's position as its key.[1] Positions are fine for a list that never reorders or shrinks. They go wrong when items move, because then React gives one item's state to whatever item now sits in that slot. Two more things: key isn't a normal prop (a component can't read props.key, it gets undefined), and keys are a React thing, not an HTML attribute, so you won't see them in the page.

3. The table's keys are positions in disguise

The games table maps twice, rows then cells (GamesTable.tsx lines 171–178):

{table.getRowModel().rows.map((row) => (
  <tr key={row.id}>
    {row.getAllCells().map((cell) => (
      <td key={cell.id} className={cls(cell.column.id)}>
        <table.FlexRender cell={cell} />
      </td>
    ))}
  </tr>
))}

row.id looks like an ID, but it comes from TanStack Table, and the useTable({ … }) call (line 120) doesn't say how to make one. In that case TanStack uses the row's index in the data array: "0", "1", "2"… (I read this in the installed library's type comments and source: getRowId "If not provided the row's index is used".)[4]

  • Sorting is fine. Sorting reorders rows but doesn't change their index in data, so each game keeps its key.
  • Filtering isn't. data is the filtered array. Type a name and the game that was at index 7 may now be at index 0, so key "0" now means a different game. React reuses that row's DOM and state for it.

Today that's harmless: the only state inside a row is the Info popover's open flag, and it closes on blur anyway. But it's exactly the bug that bites when an AI later adds per-row state (a "favourite" toggle, an expanded detail panel). The fix is one line, using BGG's real game ID, which is already in types.ts:

const table = useTable({
  features,
  columns,
  data: games,
  getRowId: (g) => String(g.id),
  …

String(g.id) is needed because getRowId must return a string and Game.id is a number. Like C#, TypeScript won't silently turn a number into a string where a string is required.

The big idea

array.map(item => <Element key={…} />) is how React draws a list. The key is how React recognises each item between renders, so it should be a stable ID from the data. Without one (or with a position dressed up as an ID, like TanStack's default row.id), state can stick to a slot instead of to the thing in it.

Practice

In TWO_ONLY.map(([value, label]) => …), what is label on the second call?

The second item is ["only", "Only"]. [value, label] unpacks it by position: value = "only", label = "Only". The index would be map's second parameter, (pair, i) =>, which this code doesn't ask for.

What happens if you delete key={value} from the radio-button <label>?

Missing keys are a development warning, not an error: React prints "Each child in a list should have a unique "key" prop." and falls back to each item's position. This list never reorders, so nothing visibly breaks. It's still worth fixing, because the warning is there to catch the lists where it does matter.

You open the score popover on one row, then click the "Name" header to sort. Why does the popover stay with the same game?

row.id is the row's index in the data array, and sorting doesn't change data, only the order rows are drawn in. So each game keeps its key, and React moves the <tr> and its state along with it. (In practice clicking the header also blurs the popover, which closes it, but the key logic is the point here.) The repo doesn't set getRowId, so the key is not the BGG ID.

An AI suggests <tr key={Math.random()}> "to guarantee unique keys". What's wrong?

Keys must be stable as well as unique. A new random key every render means React can't match any row to its previous self, so it throws away every row (and any state in it) and builds new ones each time. That's slow and loses state. react.dev warns against generating keys on the fly for exactly this reason.

The page works the same. The console shows React's "Each child in a list should have a unique "key" prop." warning, naming GamesBrowser. The tests should stay green, since a warning isn't a failure (you may see the same text printed in the test output). With getRowId the tests and build should pass. Without String(…), tsc should complain that number isn't assignable to string. I couldn't run these in this week's automated session, so tell your teacher if you see something different. That would be a good thing to dig into together.

Spaced review from lesson 0003: setFilters((f) => ({ ...f, ...patch })). Why build a new object instead of setting f.name = …? (answer, then click)

React decides whether to re-render by checking if the state is a different object. Mutating f in place leaves the same object, so React may skip the update. The spread copies f into a new object and overwrites the changed fields. That's the same "copy, don't change" idea .map() follows: it returns a new array and leaves the original alone.
