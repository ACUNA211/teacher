Filtering like LINQ: filter, some, every

What got built this week

Nothing new in two-player-bg-finder: the last commit is still 3a77ac7 (2026-09-26). So this week we read code that already exists: the function behind the filter panel, applyFilters in web/src/filters.ts, last changed in 26bb9e1.

1. One pure function decides what you see

Every time you tick a box in the filter panel, GamesBrowser.tsx runs one line:

const filtered = useMemo(() => applyFilters(games, filters), [games, filters]);

useMemo caches the result and only recomputes when games or filters change (the same dependency-array idea as useEffect in lesson 0001).[2] The interesting part is applyFilters itself. Here it is, trimmed:

export function applyFilters(games: Game[], f: Filters): Game[] {
  const name = f.name.trim().toLowerCase();
  ...
  return games.filter(
    (g) =>
      (!name || g.name.toLowerCase().includes(name)) &&
      (!f.types.length || f.types.some((t) => g.types.includes(t))) &&
      f.mustPlay.every((n) => plays(g, n)) &&
      ...
  );
}

It takes the full list and the current filter settings, and returns a new list. It changes nothing and touches no screen. That's a pure function, and it's why the AI put it in its own file instead of inside the component: a plain function is easy to test without a browser (section 3).

2. You already know these three methods

JavaScript arrays have built-in methods that take an arrow function (a lambda). They map almost one-to-one onto LINQ:

JavaScriptC# LINQReturnsOn an empty array
games.filter(g => ...)games.Where(g => ...)a new array of the items that pass[]
types.some(t => ...)types.Any(t => ...)true if at least one passesfalse
mustPlay.every(n => ...)mustPlay.All(n => ...)true if all passtrue
g.types.includes(t)g.Types.Contains(t)true if the value is in the arrayfalse

One difference: filter builds the whole new array right away. LINQ's Where is lazy until you enumerate it.[1]

Now read the filter conditions with that table in mind. Each one is joined with &&, so a game must pass all of them:

  • Types: "matches any". f.types.some(t => g.types.includes(t)): keep the game if any selected type is one of its types. Pick Strategy and Family, and a Family-only game still shows.
  • Must play: "all required". f.mustPlay.every(n => plays(g, n)): tick 3 and 4, and the game must support both player counts.
  • The empty case. Nothing selected should mean "filter is off". every on an empty array is already true, so must-play needs no guard. some on an empty array is false, which would hide every game, so the types line adds a guard first: !f.types.length || ....

That guard uses JavaScript truthiness: 0 counts as false, so !f.types.length is true when the array is empty, and || stops there without calling some. C# would make you write f.Types.Count == 0 || ...; JS accepts the number directly.[1] The !name || on the line above is the same trick: an empty string is falsy too.

The big idea

some means "any", every means "all", and they disagree about empty arrays (false vs true). When you read a filter, ask two questions: any or all? and what happens when nothing is selected? The comments in the panel ("matches any") and the test names answer both.

3. How the tests pin it down

web/src/GamesBrowser.test.tsx tests applyFilters directly, with tiny fake games. First, a helper that builds one:

function game(pos: number, over: Partial<Game> = {}): Game {
  return {
    pos, score: 100 - pos / 10, name: `Game ${pos}`, weight: 2.5, types: [], ...
    ...over,
  };
}
  • Partial<Game> is a built-in TypeScript type: the same shape as Game, but every field optional.[3] So a test can pass just { weight: null }.
  • over: Partial<Game> = {} is a default parameter, like C#'s = null optional arguments.
  • ...over is spread: copy every property of over into this new object. Later properties win, so the overrides replace the defaults. It's the C# record with expression: defaults with { Weight = null }.[1]

Then each test names one rule and checks it:

test("type matches any selected value", () => {
  const gs = [game(1, { types: ["Strategy"] }), game(2, { types: ["Family"] }), game(3, { types: ["Party"] })];
  expect(pos(applyFilters(gs, filt({ types: ["Strategy", "Family"] })))).toEqual([1, 2]);
});

test(name, fn) is an xUnit [Fact], and expect(x).toEqual(y) is Assert.Equal(y, x), comparing arrays by content.[4] pos turns the games into their numbers so the expected value reads [1, 2]. The test name is the spec: "any selected value". If someone (or the AI) changes some to every, this exact test turns red. I tried it: that's the only filter test that fails.

Practice

Nobody has picked a type, so f.types is []. What does the line (!f.types.length || f.types.some((t) => g.types.includes(t))) do?

[].length is 0, which is falsy, so !0 is true. || stops at the first true value and never calls some. The condition is true for every game, so the type filter is effectively off. Without the guard, [].some(...) would be false and every game would vanish.

What breaks if we change f.types.some(...) to f.types.every(...) on that same line?

Both compile (same signature), but the meaning flips from "any" to "all". Pick Strategy and Family and a game now needs both types, so the test type matches any selected value gets [] instead of [1, 2] and fails.

Why does the must-play line, f.mustPlay.every((n) => plays(g, n)), need no !f.mustPlay.length || guard?

"All of nothing" is true, like LINQ's All on an empty list. So with no boxes ticked, every game passes, and the test must play: blank filters nothing confirms it. mustPlay starts empty in emptyFilters(), TypeScript never adds code like this, and some on an empty array returns false.

In the test helper game(), someone moves ...over, from the end of the object to the top. What happens?

In an object literal, a later property with the same name wins. With the spread first, weight: 2.5 comes after { weight: null } and replaces it, so every fake game looks the same. I tried it: 10 of the 12 tests in that file fail.

Try it in your copy (5 minutes)

  1. In your local two-player-bg-finder, cd web, run git pull and npm install if you haven't.
  2. Run only the filter tests: npx vitest run src/GamesBrowser.test.tsx. You should see 12 passed. (The first run can be slow.)
  3. Open src/filters.ts, find the f.mustPlay.every line in applyFilters, and change every to some.
  4. Predict first: which test fails, and does an empty must-play selection still show every game? Then run the tests again.
  5. Undo the change: git checkout src/filters.ts.
What should you see? (after running it)

Ten of the 12 tests fail, not one. The default filters (emptyFilters()) start with mustPlay: [], and with some that becomes [].some(...), which is false, so every game disappears in almost every test: most failures read expected [] to deeply equal [...]. If you predicted "only the must-play test", that's the lesson: the empty case isn't an edge case here, it's the default. One word broke the whole filter, and the tests caught it in seconds.

Spaced review from lesson 0001: applyFilters reads g.maxplayers. If the scraper stopped writing maxplayers to games.json but types.ts kept it, would npm run build catch it? (answer, then click)

No. tsc checks the code against types.ts, never against games.json, which arrives at run time through fetch. The build passes; in the browser g.maxplayers is undefined, and comparisons like n <= g.maxplayers are simply false, so the must-play filter quietly hides games and the Players column shows undefined. No error anywhere, just wrong results.
