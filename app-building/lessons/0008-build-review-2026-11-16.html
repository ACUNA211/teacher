What got built this week

Nothing new in two-player-bg-finder. The last commit is still 3a77ac7 (2026-09-26), so we read existing code again. Every command you've typed in this course (npm run dev, npm test, npm run build) is defined in one short JSON file we've never opened. Today we open it.

1. One JSON file describes the project

Here's the top of web/package.json:

{
  "name": "board-games-for-two",
  "private": true,
  "type": "module",
  "scripts": {
    "dev": "vite",
    "build": "tsc -b && vite build",
    "preview": "vite preview",
    "test": "vitest run"
  },
  …

If you've edited a .csproj, you know the job: the project's name, how to build it, and which packages it needs. package.json does the same for a JavaScript project, in JSON instead of XML.

JSON looks like a JavaScript object, but it's stricter. Three rules catch people:[3]

  • Keys need double quotes: "name", never name or 'name'. Same for string values.
  • No trailing comma after the last item. "test": "vitest run", followed by } is a parse error, and npm refuses to run anything.
  • No comments. There's nowhere to write // why this is here. That's why the repo explains its choices in README.md and ADRs instead.

Two lines are not about building:

  • "private": true: "npm will refuse to publish it". A safety catch so the app never gets uploaded to the public npm registry by accident.[1]
  • "type": "module": tells Node.js to treat .js files as modern modules (the import/export you see at the top of every file). npm's own docs say npm itself ignores this field.[1]

2. scripts: named commands

Each entry in scripts is a name and a shell command. npm run build looks up "build" and runs tsc -b && vite build. npm test is a shortcut for npm run test, so it runs vitest run.[1] Think of them as saved terminal commands, like a Makefile target or a dotnet CLI verb.

But you never installed a program called vitest. How does the shell find it? npm install puts each package's command-line tools in node_modules/.bin, and npm adds that folder to the PATH while a script runs.[1] So the scripts always use the exact versions this project installed, not whatever is on your machine. (Outside a script, type npx vitest to get the same effect.)

Now the highlighted line. && is shell, not JavaScript: run the right side only if the left side succeeded. So the build is two jobs in order:

  1. tsc -b: the TypeScript compiler checks every type. tsconfig.json has "noEmit": true, so it writes no files. It only says yes or no.
  2. vite build: bundles the app into dist/ for the web.

Why both? Because Vite strips the types out without checking them. Vite's docs: "Vite only performs transpilation on .ts files and does NOT perform type checking", since checking needs the whole program and would slow Vite down. They suggest running tsc --noEmit alongside the build, which is exactly what this script does.[2] You met the same split in lesson 0001: npm run dev will happily serve code with type errors. Only the build stops you.

3. Dependencies, ^ and the lockfile

"dependencies": {
  "@tanstack/react-table": "^9.2.4",
  "react": "^19.3.0",
  "react-dom": "^19.3.0"
},
"devDependencies": {
  "@testing-library/react": "^16.3.3",
  …
  "typescript": "^7.0.2",
  "vite": "^8.3.1",
  "vitest": "^5.0.2"
}

Two lists. dependencies is what the app needs to run: React draws the page, TanStack Table builds the table. devDependencies is what you need to develop it: the compiler, the bundler, the test runner, and the @types/… packages, which hold only type descriptions (lesson 0001's "types describe, they don't load" again). npm's rule: don't put "test harnesses or transpilers" in dependencies.[1] For an app like this one, the split is mostly a label. Vite bundles only what your src/ code imports, so Vitest never reaches a visitor's browser whichever list it's in. The split matters most for libraries that other people install.

The caret. ^8.3.1 is a version range, not a version. It means "8.3.1 or newer, but below 9.0.0": keep the leftmost non-zero number fixed.[4] The idea (semantic versioning) is that a new major number signals breaking changes, so accept bug fixes and features, never a new major. In pip terms it's vite>=8.3.1,<9. NuGet's plain Version="8.3.1" is looser: a minimum with no ceiling.

The lockfile. A range alone would mean two installs a month apart could get different code. package-lock.json fixes that: it records the exact version of every package actually installed, including the packages your packages need. This repo's lockfile pins 146 packages from just 11 lines of dependencies (React is exactly 19.3.0, Vite exactly 8.3.1). It's committed to git so everyone gets the same tree. npm ci installs strictly from it: it deletes node_modules first, stops with an error if the lockfile and package.json disagree, and never rewrites either file.[1] Plain npm install may update the lockfile instead. C# has the same idea in packages.lock.json; Python's nearest is a pip freeze file.

The big idea

package.json says what the project is: its commands (scripts) and the version ranges it accepts. package-lock.json says exactly what got installed. The build script runs tsc before vite because Vite never checks types. When an AI "fixes" a build, these two files are the first place to look at what it changed.

Practice

There's no lockfile and you run npm install. Which Vite version can "vite": "^8.3.1" give you?

The caret keeps the leftmost non-zero number fixed: ^8.3.1 means >=8.3.1 <9.0.0. So 8.9.0 fits and 9.0.0 doesn't. "Exactly 8.3.1" is what the lockfile gives you. "Patches only" is the tilde, ~8.3.1.

You type npm test in web/. What actually runs?

npm test is short for npm run test, which runs the "test" script: vitest run. npm puts node_modules/.bin on the PATH first, so it's the project's own Vitest 5.0.2, not anything installed globally. The first choice is the build script; the second is dev.

What breaks if you change the build script from "tsc -b && vite build" to just "vite build"?

Vite strips types without checking them, so a type error no longer stops the build and broken code can ship. Nothing else changes: npm test is a separate script. Browsers never see types at all, so they can't report type errors.

An AI moves "vitest" from devDependencies to dependencies. What changes for people visiting the site?

The bundle is built by following imports from the app's entry point, and no app code imports Vitest. So the site is identical. It's still the wrong list (npm's docs say keep test tools out of dependencies), and it would matter if this were a library other people install. npm doesn't police which list a package is in.

Try it in your copy (5 minutes)

  1. In your local two-player-bg-finder, cd web and git pull. Open package.json and package-lock.json side by side and find "vite" in each. Which shows a range, which an exact version?
  2. Run npm ls vite. Predict first: which version will it print?
  3. Add a script: after "test": "vitest run", add a comma and a new line "typecheck": "tsc -b". Run npm run typecheck. Predict: what does it print when there are no type errors?
  4. Now break the JSON on purpose: put a comma after your new last line, then run npm test. Read the error, remove the comma, and undo everything with git checkout package.json.
What should you see? (after trying it)

package.json shows "^8.3.1" (a range); the lockfile's node_modules/vite entry shows "version": "8.3.1" (exact). npm ls vite should print 8.3.1, probably more than once, because vitest and @vitejs/plugin-react use Vite too. npm run typecheck echoes the command and then prints nothing more: silence means no type errors. With the trailing comma, npm should fail before running anything, with a JSON parse error naming package.json. I couldn't run these in this week's automated session, so tell your teacher if you see something different.

Spaced review from lesson 0002: useMemo(() => applyFilters(games, filters), [games, filters]). What is the array at the end for? (answer, then click)

It's the dependency list. React keeps the cached result and only calls applyFilters again when games or filters is a different value than last render. Leave a dependency out and the list can show stale results; it's the same idea as the [] on useEffect in App.tsx from lesson 0001.
