Show it or hide it: conditional rendering and the zero trap

What got built this week

Nothing new in two-player-bg-finder: the last commit is still 3a77ac7 (2026-09-26). So we read existing code again. Last week you learned a component is a function that returns UI. This week: how that function decides which UI to return. The app does it with two operators, all over the place, starting in web/src/App.tsx.

1. Three screens in one line: ?:

App has two pieces of state from lesson 0001: data (starts null, becomes the parsed games.json) and error (starts null, becomes a message if the download fails). Its JSX turns those into one of three screens:

{error ? <p>Could not load games: {error}</p> : data ? <GamesBrowser games={data.games} /> : <p>Loading…</p>}
{data && <Footer dumpDate={data.dump_date} scrapeDate={data.scrape_date} />}

The first line is the conditional operator, exactly C#'s cond ? a : b, chained. Read it like an if / else if / else:

StateWhat shows
error is set"Could not load games: HTTP 404" (or whatever went wrong)
no error, data is setthe filters and table (GamesBrowser)
neither yet"Loading…"

Why an expression and not an if statement? Inside JSX's { } you can only put an expression, something that produces a value, the same reason you can't put an if inside a C# $"..." string. So React code uses ?: and && where C# UI code would use if.[1]

Notice data.games in the middle branch. data is typed GamesFile | null, yet TypeScript lets you read .games there. That's narrowing: inside the "data is set" branch, the compiler knows it can't be null.[2] C# does the same flow analysis with nullable reference types.

2. && hands back a value, not a bool

The second line, {data && <Footer ... />}, means "the footer, but only once there's data". It works because of two JavaScript rules that C# doesn't have.

Rule 1: any value can stand in for true or false. In C#, if (count) won't compile. In JavaScript it's fine: a few values count as false, called falsy, and everything else is truthy.[3] The falsy ones you'll meet:

false   0   "" (empty string)   null   undefined   NaN

Empty arrays and objects ([], {}) are truthy, a classic surprise. The app uses this rule in CheckList: const shown = q ? options.filter(...) : options; where q is the search text. An empty search box is "", which is falsy, so you see every option.

Rule 2: && returns one of its operands. C#'s && always gives a bool. JavaScript's gives back the left value if it's falsy, otherwise the right value.[4]

null && "footer"     // null       (left is falsy: stop, return it)
data && "footer"     // "footer"   (data is loaded, so truthy: return the right)
0 && "footer"        // 0

Put those together with one React rule: false, null and undefined render nothing.[1] While loading, data && <Footer/> is null, so no footer. Once loaded, it's the <Footer/> element, so the footer appears.

3. The zero trap, and why the code dodges it

Now look at the last line of that table of falsy values: 0. React does render numbers, including zero. react.dev calls this out directly: don't put numbers on the left of &&, because if the left side is 0 the whole expression is 0, and React draws a 0 instead of nothing.[1]

That's exactly why the Filters button, added in 4e8bdb1, is written like this (GamesBrowser.tsx line 53):

Filters{active > 0 && ` (${active})`}

active is the number of filters in use. active > 0 is a real boolean, so with no filters the expression is false and the button just says "Filters". With two filters it's the string " (2)" (a template literal, lesson 0004) and the button says "Filters (2)". If you shortened it to active && ..., then with no filters it would be 0, and the button would read Filters0.

The same guard appears everywhere a count is involved: {value.length > 0 && ...} in CheckList, MultiSelect and RangeInput. The AI was consistent here, which is a habit worth copying when you steer it.

The big idea

JSX takes expressions, so React chooses what to show with cond ? a : b (pick one of two) and cond && a (show or show nothing). JavaScript's && returns an operand, not a bool, and React skips false, null and undefined but draws 0. So when the left side is a number, turn it into a real boolean first: count > 0 && ....

Practice

The page has just opened and games.json is still downloading. What does App show?

error and data are both still null, so the chain falls through to the last branch, "Loading…". The footer line is null && <Footer/>, which is null, and React renders nothing for null.

In plain JavaScript, what does the expression 0 && "hi" evaluate to?

&& returns its left operand when that's falsy, without looking at the right. 0 is falsy, so you get 0 itself, not false. This is the difference from C#, where && only works on bool and always gives a bool.

What breaks if line 53 changes from active > 0 && to active &&?

With no filters, active && ... is 0, and React draws numbers, so the label becomes "Filters0". TypeScript is happy: a number is something React can render. But the panel test in GamesBrowser.test.tsx starts by clicking getByRole("button", { name: "Filters" }), which no longer matches. Falsy decides which operand comes back; it doesn't make React hide it.

What breaks if we delete data && from the footer line in App.tsx?

Without the guard there's no narrowing, so data.dump_date reads a property of something typed GamesFile | null. With "strict": true in tsconfig.json, tsc reports that data is possibly null, and npm run build stops. The dev server would still start (Vite strips types without checking them[5]), and the page would then crash on load reading dump_date of null. The guard is doing real work.

Try it in your copy (5 minutes)

  1. In your local two-player-bg-finder, cd web, then git pull and npm install if you haven't.
  2. Open src/GamesBrowser.tsx and find CheckList (around line 202): {value.length > 0 && ` (${value.length})`}. Change it to {value.length && ` (${value.length})`}.
  3. Predict first: does npx tsc -b pass? What will the "More types" and "More mechanics" dropdowns say when nothing is ticked? And after you tick one box?
  4. Run npx tsc -b, then npm run dev, open the page, and open the Filters panel to check.
  5. Undo it: git checkout src/GamesBrowser.tsx.
What should you see? (after trying it)

tsc passes: 0 and a string are both things React can render, so there's no type error. On screen, the dropdowns read More types0 and More mechanics0. Tick one box and the count is 1 (truthy), so && returns the string and you see "More types (1)", which looks correct. That's what makes the zero trap sneaky: it only shows up in the empty case. Types check that code is allowed; you (and tests) check it's right.

Spaced review from lesson 0003: the Must play checkbox does update({ mustPlay: [...filters.mustPlay, n] }). Why build a new array instead of calling filters.mustPlay.push(n)? (answer, then click)

React decides whether to redraw by checking if the state is a different object. push changes the old array in place, so the state looks the same and the screen may not update. [...old, n] copies the old items into a new array with n on the end, so React sees a new value and re-renders.
