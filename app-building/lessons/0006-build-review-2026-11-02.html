1. A browser that isn't there: jsdom and render

Here is the whole of web/src/Footer.test.tsx:

import { cleanup, render, screen } from "@testing-library/react";
import { afterEach, expect, test } from "vitest";
import { Footer } from "./Footer";

afterEach(cleanup);

test("logo links to BGG, and the credit names BGG with the data dates", () => {
  render(<Footer dumpDate="2026-09-24" scrapeDate="2026-09-25" />);
  const logo = screen.getByRole("img", { name: "Powered by BGG" });
  expect(logo.closest("a")!.getAttribute("href")).toBe("https://boardgamegeek.com");
  expect(screen.getByRole("link", { name: "BoardGameGeek" })).toBeTruthy();
  expect(screen.getByText(/Ranks as of 2026-09-24; poll data fetched 2026-09-25/)).toBeTruthy();
});

Tests run in Node, not in Chrome, and Node has no web page, no document, no buttons. Vitest fixes that with one line in vite.config.ts: test: { environment: "jsdom" }. The default environment is 'node'; jsdom is a browser written in JavaScript, with a fake document that has elements, attributes and events, but draws nothing on a screen.[2]

render(<Footer ... />) comes from React Testing Library (the @testing-library/react package in devDependencies). It runs the Footer function from lesson 0004 with those props and puts the HTML it returns into jsdom's page.[1] C# comparison: it's like a WinForms test that creates the form in memory without calling Show(), then inspects its controls.

Why afterEach(cleanup)? Every test renders into the same fake page. cleanup empties it after each test, the way an xUnit test class gets a fresh instance per [Fact]. Testing Library registers that for you, but only if afterEach is a global function. In Vitest it isn't, unless you turn on the globals option, which defaults to false. So this repo calls it itself.[2] I deleted that line from GamesBrowser.test.tsx to check: two tests fail with "Found multiple elements with the role "button" and name /Next/", because the earlier tests' tables were still on the page.

2. Find things the way a person does

The test never says "the second <img>" or "the element with class bgg-logo". It says getByRole("img", { name: "Powered by BGG" }): the image a screen reader would announce as "Powered by BGG". Every element has a role (an <img> is "img", an <a href> is "link", a <button> is "button") and an accessible name, its label as a user perceives it. For an image that's its alt text. For a link or button it's the text inside, unless an aria-label overrides it.[3]

Testing Library's whole idea is that tests should use the page the way a user does. It recommends getByRole first, then getByLabelText for form inputs, and only falls back to test IDs and CSS selectors when nothing else works.[1] The payoff: the AI can rename every CSS class or reorder the markup, and the tests still pass. They only fail when something a user would notice changes.

The getBy... queries are strict. If they find nothing, or more than one match, they throw, and the test fails right there. (There is also queryBy..., which returns null instead of throwing. The repo uses queryAllByRole to check that a list is empty.) So expect(screen.getByRole("link", { name: "BoardGameGeek" })).toBeTruthy() reads oddly, but the real check is the getBy itself. The expect just makes the intent obvious.

Two bits of TypeScript in that test:

  • logo.closest("a")!: closest walks up to the nearest <a> and returns HTMLAnchorElement | null. The postfix ! is the non-null assertion: "trust me, it isn't null". C# 8 has the same operator (the null-forgiving !).
  • screen.getByLabelText(...) as HTMLInputElement (in the next test) is a type assertion. It looks like a C# cast (HTMLInputElement)x, but it isn't one: C# checks the cast at run time and throws InvalidCastException, while TypeScript's as and ! are simply erased. I compiled both to be sure: el as HTMLInputElement becomes plain el, and el!.closest("a") becomes el.closest("a"). They change what the compiler believes, not what the code does (lesson 0001's "types are a promise" again).

3. Act, then assert: fireEvent

The min-votes box is supposed to snap back up to 15 if you type something lower and leave the field. Here's the test, GamesBrowser.test.tsx lines 78–85:

test("min votes input defaults to 15 and snaps back up on blur", () => {
  render(<GamesBrowser games={[game(1)]} />);
  const input = screen.getByLabelText("Votes at 2 min") as HTMLInputElement;
  expect(input.value).toBe("15");
  fireEvent.change(input, { target: { value: "3" } });
  fireEvent.blur(input);
  expect(input.value).toBe("15");
});

It's the classic Arrange, Act, Assert you'd write in xUnit, with the user's actions in the middle:

  • Find: "Votes at 2 min" is the input's aria-label, built in GamesBrowser.tsx line 163 as {`${label} min`} (a template literal from lesson 0004).
  • Type: fireEvent.change(input, { target: { value: "3" } }) sets the box to "3" and fires a change event, so React's onChange handler runs, exactly as if you'd typed.
  • Leave: fireEvent.blur(input) fires blur, the event for "focus left this field". That triggers the component's onBlur: onChange({ ...value, min: Math.max(floor, value.min ?? floor) }), which raises 3 back to the floor of 15.

Notice that input.value is always a string ("15", not 15), even on a type="number" input. That's the web platform: form fields hold text, which is why the component has a toNum helper to convert it.[3]

I checked that this test really guards the behaviour: with the onBlur line removed, it's the only one of the 23 tests that fails, with expected '3' to be '15'.

The big idea

Component tests draw the real component into a fake browser (render + jsdom), find elements by what a user perceives (getByRole, getByLabelText: role plus accessible name), act like a user (fireEvent.click, .change, .blur), and then assert on what the user would see. getBy throws on zero or several matches, so finding an element is already a check.

Practice

In the footer test, what does screen.getByRole("img", { name: "Powered by BGG" }) return?

For an <img>, the accessible name is its alt text, and Footer.tsx has alt="Powered by BGG". The query returns that element in jsdom's page. It never touches the file on disk, and CSS classes play no part in it.

What breaks if we delete fireEvent.blur(input); from the min-votes test?

The snap-back lives in onBlur, not onChange. onChange just stores what you typed. Without the blur event, nothing raises 3 back to 15, so the last expect sees "3" and the test goes red. fireEvent calls are synchronous: nothing waits.

You ask the AI to "make the logo alt text more descriptive" and it changes it to alt="BGG logo". What happens on npm test?

I tried it. getByRole finds no image named "Powered by BGG" and throws: Unable to find an accessible element with the role "img" and name "Powered by BGG". That's a good failure: BGG's terms require that logo, and the test is the reminder. alt is a string either way, so tsc has nothing to say.

Why does each test file in this repo start with afterEach(cleanup)?

All tests share one jsdom page. Testing Library only cleans it up automatically when afterEach is a global, and Vitest's globals option is off by default. Without cleanup, the second render adds a second table, and getByRole("button", { name: /Next/ }) throws "Found multiple elements".

Try it in your copy (5 minutes)

  1. In your local two-player-bg-finder, cd web, then git pull and npm install if you haven't. Run npm test: you should see 23 passed.
  2. Open src/GamesBrowser.tsx and find the Filters button (around line 53). Wrap the word in a <span className="label">, so it reads <span className="label">Filters</span>{active > 0 && ...}.
  3. Predict first: the panel test does getByRole("button", { name: "Filters" }). Does it still pass?
  4. Run npm test. Then try a change a user would notice: rename the text to Filter and run it again.
  5. Undo it: git checkout src/GamesBrowser.tsx.
What should you see? (after trying it)

With the <span>, everything still passes. A button's accessible name is all the text inside it, however it's nested, so a user (and the test) still sees a button called "Filters". Renaming it to "Filter" fails the panel test with "Unable to find an accessible element with the role "button" and name "Filters"". Markup changes are free; visible changes get caught. That's the point of querying by role.

Spaced review from lesson 0005: the button code is Filters{active > 0 && ` (${active})`}. With no filters on, why doesn't the button say "Filters0"? (answer, then click)

active > 0 is a real boolean. With no filters it's false, && returns false, and React renders nothing for false. Plain active && ... would return the number 0, and React does draw numbers. Today's lesson adds that a test would catch it: getByRole("button", { name: "Filters" }) wouldn't match "Filters0".
