Types are a promise, not a check

About 10 minutes. By the end you can read types.ts and the data-loading code in Board Games for Two, and you know which command catches a type mistake and which ones don't.

What got built this week

A lot: two-player-bg-finder went from a plan to a deployed app in 22 commits. A Python scraper writes web/public/games.json (3,638 games), and a Vite + React app shows it as a sortable, filterable table. We'll skip the filter panel for now and look at the foundation everything else stands on: how the app knows what a game looks like. It came in 1f93002 (the web app) and changed in dfcae09 (the new two-player score).

1. The JSON file and the type that describes it

JSON is plain text for data: objects in { } with "key": value pairs, arrays in [ ], plus strings, numbers, true/false and null. One game in games.json looks like this (trimmed):

{"dump_date": "2026-09-25", "scrape_date": "2026-09-26",
 "games": [{"id": 187645, "name": "Star Wars: Rebellion", "year": 2016,
            "weight": 3.751, "mechanics": ["Dice Rolling", "Hand Management"], ...}]}

The app describes that shape in web/src/types.ts:

// Mirrors the games.json schema in scraper/README.md.
export type GamesFile = {
  dump_date: string;
  scrape_date: string;
  games: Game[];
};

export type Game = {
  score: number;
  name: string;
  year: number | null;
  mechanics: string[];
  ...
};

Reading it as a C# developer:

TypeScriptClosest C#Meaning
export type Game = { ... }public record Game { ... }A named shape. export lets other files import it, like public.
numberdoubleJavaScript has one number type for ints and decimals.
number | nullint?A union: either a number or null. Some games have no year on record.
string[]string[] / List<string>An array of strings. JS arrays grow, like a List.

Why a separate file? Every component (GamesTable, GamesBrowser, filters.ts) imports Game from one place, so the editor can autocomplete g.poll_score and the compiler can flag g.pol_score. When the scraper started writing three new fields in dfcae09, the same commit added them here:

   score: number;
+  poll_score: number;
+  poll_pct: number;
+  geek_pct: number;

That "change the JSON, change the type in the same commit" habit is the whole point of this lesson, because nothing else keeps them in sync.

2. Where the JSON enters the app

web/src/App.tsx downloads the file when the page opens:

const [data, setData] = useState<GamesFile | null>(null);
const [error, setError] = useState<string | null>(null);

useEffect(() => {
  fetch("/games.json")
    .then((r) => (r.ok ? r.json() : Promise.reject(new Error(`HTTP ${r.status}`))))
    .then(setData, (e: Error) => setError(e.message));
}, []);
  • useState<GamesFile | null>(null): a piece of component state that starts as null ("not loaded yet"). The <...> is a generic type argument, exactly like C#'s List<Game>. It returns a pair, unpacked with const [data, setData] = ... (like a C# tuple deconstruction).[1]
  • (r) => ... is an arrow function, the same as a C# lambda.
  • fetch(...) returns a Promise, JavaScript's Task. .then(onSuccess, onFailure) is like ContinueWith: run this when the value arrives.
  • useEffect(..., []) runs the code after the component first appears on screen. The empty array means "no dependencies, so don't run it again".[1]

Now the key line. The type library that ships with TypeScript declares json(): Promise<any>. any means "don't check this". So when setData receives the parsed file, TypeScript simply believes it's a GamesFile. Nothing looks inside.

The big idea

In C#, JsonSerializer.Deserialize<Game>() builds a real Game object, and the type exists at runtime. TypeScript types are erased: the compiler checks them, then deletes them, and the browser runs plain JavaScript.[2] So types.ts is a promise about games.json, and only you (and the scraper) keep it.

Which command checks the types?

Look at the scripts in web/package.json:

"build": "tsc -b && vite build",
"test": "vitest run"

tsc -b is the TypeScript compiler, run only to type-check (the tsconfig.json has "noEmit": true). Then Vite bundles. Vitest strips the types without checking them, so npm test can pass while the build fails.[3] I tried it on the repo: deleting poll_pct from types.ts leaves all 23 tests green, while tsc reports three errors. And neither command reads public/games.json: it's fetched in the browser, outside the compiler's view.

Practice

What does <GamesFile | null> tell TypeScript in useState<GamesFile | null>(null)?

It's a generic type argument with a union: data is either a GamesFile or null (not loaded yet). It checks nothing at runtime, downloads nothing (that's fetch), and a list would be GamesFile[].

The scraper renames poll_pct to poll_percent in games.json, but nobody updates types.ts. You run npm test and npm run build. What happens?

The tests build their own fake games, and tsc never sees games.json (it's fetched at runtime). In the browser, g.poll_pct is now undefined, and pct(v) in GamesTable.tsx calls v.toFixed(1) on it: a TypeError ("Cannot read properties of undefined") while rendering the table.

What breaks if we delete the , [] at the end of the useEffect call in App.tsx?

With no dependency array, an effect runs after every render.[1] Here setData stores a new object, which causes a re-render, which runs the effect, which fetches again: a loop of downloads. The [] means "only after the first render". It still compiles either way.

The Year column renders c.getValue() ?? "–", where the value comes from year: number | null. What does ?? do?

It's the same null-coalescing operator as C#: use the right side only when the left is null or undefined. A year of 0 would still show 0. (num() turns null into undefined first so the table sorts missing years last.) The | null in the type is what reminds the author to handle it.

Try it in your copy (5 minutes)

  1. In your local two-player-bg-finder, cd web and run npm install if you haven't.
  2. Open src/types.ts and delete the line poll_pct: number;.
  3. Predict first, then run npm test, then npx tsc -b. Which one complains, and in which files?
  4. Undo the change (git checkout src/types.ts).
What should you see? (after running it)

npm test: 23 passed. npx tsc -b: three errors. GamesTable.tsx says Property 'poll_pct' does not exist on type 'Game', and both test files say Object literal may only specify known properties, because their fake game() helpers still set poll_pct. Takeaway: before trusting a green test run, run npm run build too.

From memory: why can't TypeScript warn you when games.json stops matching types.ts? (then click to check)

Types are erased before the code runs, the file arrives at runtime through fetch, and r.json() is typed any, so the compiler never compares the real data to the type.
