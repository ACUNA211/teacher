Components are functions: props and children in the Info popover

About 10 minutes. By the end you can read a component's signature in Board Games for Two, say which value goes into which prop when you see <Info ...>...</Info>, and predict what TypeScript and the tests say when a prop goes missing.

What got built this week

Nothing new in two-player-bg-finder: the last commit is still 3a77ac7 (2026-09-26). So we read existing code again. Three lessons in, we've used components without ever asking what one is. The smallest one in the app is a good place to ask: Info in web/src/GamesTable.tsx, the little popover behind every Two-player score. It came in 248ed69 ("score popovers").

1. A component is a function that takes one object

Here is the whole component:

export function Info({ label, children, name }: { label: ReactNode; children: ReactNode; name?: string }) {
  const [open, setOpen] = useState(false);
  return (
    <span className={`info${open ? " open" : ""}`}>
      <button type="button" aria-label={name} aria-expanded={open}
              onClick={() => setOpen(!open)} onBlur={() => setOpen(false)}>
        {label}
      </button>
      <span role="tooltip" className="info-pop">{children}</span>
    </span>
  );
}

Strip away the JSX and it's an ordinary function: it takes one argument, an object called the props, and returns a description of what to draw.[1] The name starts with a capital letter on purpose: that's how JSX tells your <Info> apart from a built-in tag like <span>.[2]

The highlighted parameter packs two things into one line. Read it from the colon:

  • After the colon, the type: { label: ReactNode; children: ReactNode; name?: string }. An inline object type, like a type Game = {...} from lesson 0001 that was never given a name.
  • Before the colon, destructuring: { label, children, name } pulls the three fields out into local variables. It's the object version of the const [a, b] = ... you saw in lesson 0003.[3]
  • name?: string: the ? makes the prop optional. A caller may leave it out, and inside the function it's then undefined.[4]
  • ReactNode means "anything React can draw". In the installed @types/react it's a union: an element, a string, a number, a boolean, null, undefined, or a list of those, and a few rarer cases.

2. Calling it: attributes and children become props

You never call Info(...) yourself. You write JSX, and React calls the function. Here's the Two-player score cell:

<Info label={fixed(1)(g.score)} name={`Two-player score ${fixed(1)(g.score)}: show breakdown`}>
  Poll at 2 beats {pct(g.poll_pct)} of games · Geek rating beats {pct(g.geek_pct)}
</Info>

Each attribute becomes a field of the props object. Whatever sits between the opening and closing tags becomes one more field, named children.[1] So this JSX hands Info roughly { label: "99.9", name: "Two-player score 99.9: show breakdown", children: [...] }. Two bits of syntax to read:

  • { } in JSX means "evaluate this JavaScript" (lesson 0003). A plain "..." passes a fixed string, as in label="ⓘ" on the column header.
  • `Two-player score ${...}` with backticks is a template literal: C#'s $"Two-player score {...}".[5] The same trick builds the class name: `info${open ? " open" : ""}` gives "info" or "info open".

The compiler checks every one of these calls against the props type. I added a call with no label and ran npx tsc -b:

error TS2741: Property 'label' is missing in type '{ name: string; children: string; }'
  but required in type '{ label: ReactNode; children: ReactNode; name?: string | undefined; }'.

Look at the left side of that message: children: string. The text hi I'd put between the tags really did arrive as a prop called children. The message is the proof of this section.

3. Each copy gets its own state

Info calls useState(false). With 100 rows on a page there are more than 100 Infos on screen, and each one has its own open. State belongs to one place in the tree, not to the function.[6] Think C# instances: the function is the class, each <Info> on screen is an instance, and open is an instance field. Tap row 1's score and only row 1's popover opens.

What does open actually do? It adds the open class, and the CSS in index.css does the rest:

.info-pop { display: none; ... }
.info:hover .info-pop, .info.open .info-pop { display: block; }

So a mouse gets the popover from CSS :hover alone, with no JavaScript. The state is for touch screens and keyboards, where there is no hover: tap to toggle, and onBlur (focus leaves the button) closes it. aria-expanded={open} tells a screen reader whether it's showing, and aria-label={name} gives the button a readable name, which is also how the tests find it.

The big idea

A component is a function from props (one object, typed like any parameter) to UI. JSX attributes fill the props, and the content between the tags arrives as children. TypeScript checks every call site, just as C# checks method arguments. State lives in each copy on screen, not in the function, so reusable pieces like Info stay independent.

Practice

In Info's props type, what does the ? in name?: string mean?

? marks an optional property: if the caller omits it, it's undefined inside the function, like a C# optional parameter defaulting to null. It's still a string when given, and the check still happens at compile time (types are erased at run time, lesson 0001).

Someone writes <Info name="x">hi</Info> somewhere in the app. What does npm run build do?

build runs tsc -b first, and label has no ?, so it's required: error TS2741, "Property 'label' is missing". I tried it. "hi" is fine as children, because a string is a ReactNode.

What breaks if we replace {children} inside Info with {null}?

All Infos share the one function, so every popover (score breakdowns, poll bars, the header ⓘ) shows an empty box. An unused variable isn't a type error here. I tried it: only "tapping a score shows its breakdown" fails, because it's the one test that looks for the popover's text. The other 22 still pass.

On a phone, you tap the score in row 1 and its breakdown opens. What happens to row 2's popover?

Each <Info> on screen keeps its own open. Sharing a function doesn't share state, just as two instances of a C# class don't share instance fields. The CSS rule needs .info.open on that span, and only row 1's span got the class.

Try it in your copy (5 minutes)

  1. In your local two-player-bg-finder, cd web, then git pull and npm install if you haven't.
  2. Run npx vitest run src/GamesTable.test.tsx. All 10 tests should pass.
  3. Open src/GamesTable.tsx, find the header popover (around line 160): <Info label="ⓘ" name="How the Two-player score is calculated">. Delete the name="..." attribute.
  4. Predict first: does npx tsc -b pass? Does the test file pass? Then run both.
  5. Undo it: git checkout src/GamesTable.tsx.
What should you see? (after trying it)

tsc passes: name is optional, so leaving it out is legal. But one test fails: Unable to find an accessible element with the role "button" and name "How the Two-player score is calculated". Without aria-label the button's accessible name is just "ⓘ", so a screen reader user, and the test, can't tell what it's for. Types check that calls are allowed; tests check that they're right. You need both.

Spaced review from lesson 0001: TypeScript caught a missing label at build time. Would it catch games.json losing a field that types.ts still lists? (answer, then click)

No. tsc checks your code against the types: every <Info> call is code, so it gets checked. games.json is data that arrives at run time through fetch, after the types have been erased. The build passes and the problem shows up in the browser as undefined.
